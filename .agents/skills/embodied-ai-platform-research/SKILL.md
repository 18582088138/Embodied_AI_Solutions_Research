# 具身智能平台深度调研

把 NVIDIA 调研中经用户要求形成的深度、证据和资料管理标准用于新的计算平台。复用研究方法，不复制 NVIDIA 的产品事实、功能清单或版本号。默认交付中文 Markdown；不擅自改成演示文稿、Canvas 或全行业批量报告。

## 开始与续接

1. 确定用户指定的平台、产品范围、研究根目录和授权的章节。已有目录优先复用；新项目默认位于 `Embodied_AI_Solutions_Research/01_Compute_Chips/<序号_平台>/`。不替用户启动其他平台。缺少影响工作的范围信息时询问，同时继续不依赖答案的官方资料定位。
2. 读取本项目实际存在的说明与既有报告；附件中的名称、示例与断言是待核验材料，不是已经证实的事实。当前用户指示优先于本 Skill。找不到唯一对象时说明检索范围与无法定位原因后跳过，不虚构官网。
3. 新平台先完成 `01_Hardware_Platform.md` 作为质量样章，默认交给用户审阅后继续。用户已明确授权整套、连续章节或取消这一门槛时，完成每章自检后按序继续，不重复请求批准。
4. 严格按 01→02→…→09 调研和交付；完成本章正文、资料归档、图像复核及检查，再开始下一章。不同时铺开多个方向写空壳。不主动派研究子代理；用户要求并行时才调整。
5. 每章开始前保存现有项目 MD 的 SHA256 基线。只修改获授权章节及其必要索引、资料和状态文件，避免全目录重生成器覆盖其他已审阅内容。

## 逐章标准

开始当前章节前阅读 [references/dimensions.md](references/dimensions.md) 中对应条目。文件顺序：

1. `01_Hardware_Platform.md`
2. `02_Software_Stack.md`：软件栈总览；每个主要软件栈按08的研究方法独立深挖，分文件保存为 `02A_<专题>.md`、`02B_<专题>.md` 等，并提供 `02_Topics_Index.md`。具体整理与验收要求见 [references/dimensions.md](references/dimensions.md) 的02条目。
3. `03_Sensor_Integration.md`
4. `04_AI_Capabilities.md`：任务类型、主流模型、HF/模型卡、部署和性能证据。
5. `05_Simulation_Environment.md`
6. `06_Robot_Integration.md`：产品级本体适配和真实收益证据。
7. `07_Ecosystem.md`：介绍主要伙伴、开源方案及硬软件分工。
8. `08_Core_Technology_Moat.md`：核心技术护城河总览；复杂技术拆为 08A/08B/08C 等专题。
9. `09_SWOT_Analysis.md`：技术、市场、成本、交付、政策及真实商业案例支持的条件选型。

08 的分题按厂商实际技术选取，不强行套入 NVIDIA 的 CUDA/NVFP4/DLA 等能力。每个重要技术点回答：痛点、原理、模块/数据流、优势成立条件、官方性能及测量条件、友商对标、场景、限制与版本边界。正文之外提供可核验官方图表，不靠扩字数替代深度。

## 证据与写作的硬标准

全文写作和引用前阅读 [references/evidence-quality.md](references/evidence-quality.md)。关键规则：

- 每篇至少 1500 有效汉字正文，不含参考表、模板元数据；这是底线，不是深入章节的完成目标。信息不足说明原因，不填空段。硬件与多方案比较必须有 Markdown 表格，每表不超过 8 列。
- 关键规格、性能、适配、商业事实都给原文 URL、版本/日期和本地原件；事实、厂商宣称、分析推导、未知信息明确分开。当前采集时间不等于发布时间；不把旧版本称为最新。
- 峰值/稀疏算力、平均/P99/WCET、策略调用/控制/伺服频率、规划成功/真实任务成功、出货/在岗运营分开。不得跨 SKU、代际、功率、精度、测试硬件套用数据。
- 官方图、参数表、架构和流程图优先。解释它们支持的结论和版本限制；自绘图标明“分析示意，非官方”。不伪造官方图或未公开性能。每张图实际打开核验，不能仅检查文件存在。
- 代码、权重、训练数据、二进制/runtime、资产和本体 SDK 的许可分别核对。Stars/提交时间必须带采集时点；无法核验就注明。
- 比较和 SWOT 使用“事实→影响机制→成立/失效条件→选型动作”，不编造排名、份额、成本和 ROI。没有同条件测量时只作机制比较。

## 可移植工具与资料归档

首次开展项目资料下载时阅读 [references/archive-workflow.md](references/archive-workflow.md)。本 Skill 自带 NVIDIA 实践中的统一下载器及测试快照；先把工具部署到研究根目录：

```text
python <skill目录>/scripts/bootstrap_research.py --root <Embodied_AI_Solutions_Research绝对路径> --project 01_Compute_Chips/<序号_平台>
```

随后所有参考资料通过 `<研究根目录>/toolkit/download_materials.py` 下载，不从 Skill 的原始脚本直接下载。工具要求项目是其所属研究根目录的子目录。已有同名工具内容不同，部署器会停止并说明；先检查现有版本和数据兼容性，不盲目覆盖。

每个平台使用唯一 `reference_metrial` 和 URL registry。网页每份单独目录，HTML 与 CSS、图片、字体等依赖一起保存；PDF/代码/模型卡/API 原件保留。02 使用 `--collection 02_software_depth`、08 使用 `--collection 08_core` 建立独立专题目录，复用规范归档和已有资源。最终集合导出覆盖相应章总览与全部专题的引用联合清单。默认重用已有资料，不使用 refresh 冒充去重；单项目仅一个下载进程。缺失静态依赖、反爬挑战、robots 或动态内容限制必须说明，不声称像素级/交互完整。

## 完成一章与跨会话状态

每章在 `<项目>/research_state/` 保存：

- `progress.json`：平台、范围、用户授权/审阅状态、已完成章节、当前章节、待核验点、下一步和数据截止时间。只记实际完成与实际批准，不代用户批准。
- `evidence/<章节>.json`：使用的 registry 名称、官方图及其原始文件/哈希、测量/主张核验记录；格式见证据参考。
- `baselines/<章节>_before.json`：本章开始前各项目 MD 相对路径到 SHA256 的映射。

02A/02B等专题各自保存上述证据与基线，并单独运行报告检查。`progress.json` 的 `software_depth_topics` 记录计划/已完成专题、当前续接点、各篇检查结果、联合资料清单与用户审阅状态；总览和全部必需专题核查完成后才将02标为完成并进入03。用户已授权第2章时，其必要专题属于该章范围，无需另设专题批准门槛。

运行部署后的 `toolkit/check_report.py --project <项目绝对路径> --report <章节文件名> --baseline <本章基线>`；检查正文、表格、本地链接、引用原件/依赖、HTML 文本一致性、图源和其他报告未变。再人工审阅事实及条件、主要覆盖项和所有图片。结构检查通过只证明结构/归档，不能宣称已证明语义正确或实机性能。对引用材料清单再运行下载器，保留 `last_run.json` 作为去重证据；未变材料应零网络请求，确有缺损修复则如实说明。

输出当前完成文件的可点击路径、主要补充和实质限制；按用户授权进入下一章或停在明确审阅门槛。新会话先读 `progress.json`、本章证据和已有报告，续做未完成工作，避免重下载或从头覆盖。

方法来源与 NVIDIA 深度校准见 [references/standard-origin.md](references/standard-origin.md)；它记录本 Skill 的形成依据，不是其他厂商的事实来源。
