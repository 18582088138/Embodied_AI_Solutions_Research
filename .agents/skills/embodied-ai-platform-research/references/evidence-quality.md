# 证据、图文与质量检查

## 可追溯研究

研究当前实际时点的官方材料，优先最新产品/release文档；旧版资料只支持该版本。检索依次扩展产品/规格→开发/API/调优指南→源码/model card→论文/白皮书/技术blog→伙伴/整机/客户公告→财报/协会/法规。可用英文、中文、产品旧名和准确SDK/SKU关键词；网页搜索片段只是定位线索，正文与PDF需实际读取。连续几次无效路径后转向官方目录/链接，不无限猜URL或绕过访问限制。

每项关键主张记录：主张、原文位置/页码、准确引用、原始URL、材料发布时间/版本、采集时间、产品/平台、测试条件、证据类型、可推导结论、不能推导项。必要时追到底层API/源码，而不是只转述厂商宣传。找不到信息区分：官方未披露、本文未取得、证据冲突、版本不适用、对象不能唯一定位。不要把下载失败描述成厂商未披露。

事实可直接转述；未经独立测量的宣称注明“厂商称”；推导注明“分析/假设计算”，给公式与输入；未证实的未来状态注明计划。避免“据悉”“领先”“性能大幅提升”而无对应指标。

## 数字和适配边界

- 算力：位宽/格式、dense/sparse、理论峰值、功率/频率、SKU与平台。
- 推理：模型/版本、batch、shape/相机、迭代、精度、输入/输出、预处理/RPC包含与否、样本、warmup、统计量。
- 频率：采集、policy-call、规划、控制器、总线、伺服分别记录。
- 控制：规划成功、轨迹可执行、真实任务完成和危险响应不是同一指标；P99不是WCET/硬实时保证。
- 商业：出货、样本销量、合同、试点、在岗数量、累计完成、尝试次数、暴露小时、利润/ROI各自需要分母与证据。
- 百分比与百分点分开；基准表保留原始精度，不凭图片展示精度补出更精确数据。公式上限/理想带宽分析不当硬件实测。

## 图表处理

重要复杂系统需官方图/表/架构/流程辅助。先寻找已下载HTML的图片assets和PDF原页；确需额外资源URL仍通过统一下载器，不写第二套网络脚本。原文件保留，衍生图放 `reference_metrial/derived/figures/`，记录来源、页码/原图URL、版本、原件/衍生哈希、渲染/裁剪操作。

PDF可用Poppler渲染后裁剪，但保留标题、坐标/单位、图例及caption和完整PDF。SVG存在foreignObject时普通图像转换可能丢字，必要时用本地浏览器渲染；GIF选择能完整表达机制的帧并说明原动画仍保留。实际打开逐图核查，防止空白、截断、乱码或用动画首帧代替完整机制。联系表用于总览，不替代关键图放大检查。

正文中解释图支持什么结论、不能证明什么；自绘Mermaid等标明“基于公开材料整理，非官方图”。报告图路径与文件链接采用实际存在的仓库内相对路径；证据 JSON 使用仓库根相对路径。研究尚未完成时跨报告使用文字引用，不创建不存在的链接或锚点。

## 持续状态和证据JSON

`progress.json` 建议字段：`platform`、`scope`、`data_cutoff`、`authorization`（实际用户授权文字摘要）、`review_status`、`completed_dimensions`、`current_dimension`、`pending_evidence`、`next_step`。不要保存账户凭据。`completed`意味着资料和正文已核查，不等于用户批准。

每章 `research_state/evidence/<stem>.json` 用以下结构。记录名称必须与当前项目registry一致；不填示例虚构来源。

```json
{
  "source_ids": ["registry中已成功核验的名称"],
  "figures": [
    {
      "file": "本地官方图或衍生图的仓库根相对路径",
      "sha256": "实际衍生文件哈希",
      "source_id": "该图所属registry名称",
      "source_url": "原始图URL或原PDF URL",
      "original_file": "registry所指原文或其中已下载asset的绝对路径",
      "original_sha256": "原文件实际哈希",
      "operation": "原件，或准确页码/裁剪/渲染操作"
    }
  ],
  "claim_review": [
    {
      "claim": "关键主张",
      "source_id": "对应名称",
      "location": "章节/页码/API符号",
      "evidence_type": "事实/厂商宣称/分析/未知",
      "conditions": "SKU、版本、硬件和测量口径",
      "finding": "人工核验结果及边界"
    }
  ],
  "manual_review": {
    "coverage": "对应维度覆盖/缺口说明",
    "versions_and_measurements": "核对结果",
    "maturity_and_licenses": "适配成熟度及许可核对",
    "figures_opened": "逐图查看结果；无官方图说明检索及原因"
  }
}
```

`check_report.py`接受上述trace，自动检查正文、表格、本地链接、registry正文/依赖、原件哈希、HTML文本及图源，支持基线保护。`claim_review`和`manual_review`用于人工审阅，工具只检查存在与结构，不给内容盖“事实正确”章。未核验挑战页、Git LFS指针、目录导航或空壳页面不得作为有效来源，即使HTTP200。

## 完成门槛

1. 当前维度的关键主题实际深入展开，至少1500有效汉字；不能靠参考表或重复介绍凑量。
2. 重要主张有正文级来源及条件；原文与本地归档一一对应，许可和成熟度边界已核。
3. 所有图片已打开核查；表格有数据、列数一致且≤8列；无未创建文件链接。
4. 所有引用正文成功取得，缺失依赖如实列出；失败候选可以留在registry研究日志中，但不得进入有效引用清单。
5. 自动检查通过，并人工完成语义/覆盖审阅；其他已审阅MD与基线一致。
6. 最终复用清单的下载运行证明去重；章节、证据、审阅和下一步写入状态文件。不得将离线检查描述为已做硬件/机器人实机测试。
