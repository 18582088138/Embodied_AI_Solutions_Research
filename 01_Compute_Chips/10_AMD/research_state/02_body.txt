## 3. ROCm Core SDK：驱动、计算库和发行机制

ROCm 10.1.0 是由 TheRock 构建的 Core SDK 生产发行，迁移始于 7.14.0。它不是仅将旧 SDK 版本号加大：安装目录改为 `/opt/rocm/core-10.1`，包名前缀改为 `amdrocm-`，Extras 使用 `/opt/rocm/extras-10`。通过系统包管理器安装的元包会配置 alternatives 和部分 `/opt/rocm` 兼容链接；tarball 不替用户解析依赖或建立这些链接。旧脚本能找到路径，不代表它已加载期望 ABI/架构库。@@AMD_ROCm_Transition@@

驱动在宿主机提供设备访问，Core SDK 提供用户态编译、runtime 和计算库，框架 wheel 则另行分发。容器中的 GPU 推理仍依赖宿主驱动和 `/dev/kfd`、`/dev/dri`。APU 表要求所列 Ubuntu 内核的 inbox driver，应先看 APU 条件，再决定是否安装独立驱动。数据中心 PLDM/IFWI 和虚拟化驱动的限制单列，不能作为端侧 NPU 的固件要求。@@AMD_ROCm_Compatibility@@ @@AMD_ROCm_PyTorch@@

| 模块组 | 10.1.0 矩阵中的独立组件版本 | 输入 / 执行角色 | 机器人软件中的接口意义 |
|---|---|---|---|
| 编译 / runtime | HIP 7.16.0、HIPIFY 10.1.0、LLVM 24.0.0、ROCr 1.21.0 | kernel 编译和设备执行 | CUDA 移植、自定义算子；不是 NPU compiler |
| 矩阵 / 神经网络 | rocBLAS 5.7.0、MIOpen 3.6.1、hipBLASLt 1.4.1 | 矩阵运算、DNN primitives | 框架底层实现，算法选择受 shape/精度影响 |
| 通信 | RCCL 2.30.7、rocSHMEM 3.7.0 | GPU 集合通信 / 共享内存通信 | 分布式训练基础；不同于 ROS DDS |
| 媒体 / 视觉 | rocDecode 1.10.0、rocJPEG 1.10.0、RPP 3.2.0 | 解码、图像及数据处理 | 可用于感知前处理，需查具体 GPU backend |
| 可观测性 | AMD SMI 27.1.0、Compute Profiler 3.9.0、Systems Profiler 1.9.0、Profiler SDK 1.4.1 | 设备状态、计数器、系统 timeline | 区分计算瓶颈与拷贝/CPU/调度等待 |

这些组件归入统一发行，不共用同一版本号，也不保证 Linux/Windows、CDNA/RDNA 都提供同一功能。TheRock 将部分组件移到 Extras 或 standalone 发行，旧“装一个 ROCm 元包即可得到全部工具”需要修订。RPP 3.2.0 移除 OpenCL backend 并统一 HOST/HIP API；ROCm SMI 已弃用、标准构建不再构建/安装，监控新方案应转 AMD SMI。release known-issue 中仍有 `rocm-smi` 命令，是迁移残留，不能据此承诺新环境带该工具。@@AMD_ROCm_Compatibility@@ @@AMD_ROCm_Transition@@ @@AMD_ROCm_Release@@

**分析：**具身软件如果通过 Python 框架使用 GPU，先固定框架环境和目标架构；只有开发自定义 C++/HIP kernel 时再完整锁定 compiler/dev 包。镜像应记录驱动、Core SDK、框架、架构库、模型 hash 与启动参数。只保存 `requirements.txt` 无法复建宿主驱动和设备固件，也无法控制同一机器上不同 ROCm prefix 混用。

## 4. HIP / HIPIFY：执行模型与内存语义

HIP 提供 C++ GPU 编程与 runtime API；HIPIFY 用于 CUDA 源码/API 迁移。框架中保留 `torch.cuda` 命名不表示实际用了 NVIDIA GPU。移植的目标是源代码与调用路径：涉及 CUDA 私有库、架构指令、inline PTX、特殊同步机制时仍需逐项替换和验证，不能把“可转换”当成“等性能、等数值结果”。@@AMD_HIP_Docs@@ @@AMD_HIPIFY_Docs@@ @@AMD_ROCm_PyTorch@@

典型执行链是分配设备/主机缓冲区→上传→提交 kernel→记录 event→依赖 stream 等待→回读结果。`hipStreamCreate`、`hipMemcpyAsync`、`hipEventRecord`、`hipStreamWaitEvent` 和 `hipStreamSynchronize` 分别控制队列、传输、依赖和 host 等待。非阻塞 stream 允许并行提交，但是否重叠还取决于 async engine、kernel 的寄存器/共享内存占用及竞争资源。官方异步指南明确指出并发 kernel 的执行时间可能因资源争用增加，应看 timeline，不仅看单个 kernel timer。@@AMD_HIP_Async@@

HIP 的 unified address space、managed memory、APU 物理共享 DRAM 是三个需要分清的层次。`hipMallocManaged` 的页迁移依赖 GPU、HMM 内核与 `HSA_XNACK`；API 可调用不表示所有设备支持按访问迁移。`hipDeviceGetAttribute` 可查询 ManagedMemory、PageableMemoryAccess、ConcurrentManagedAccess 等能力，不能把 CDNA 表中的能力套给 R9700 或 X199。页错误、首次迁移和远端访问都可能增加首帧与尾时延。@@AMD_HIP_Memory@@

| 内存 / 执行选择 | 解决的需求 | 必须检查的条件 | 不成立的推论 |
|---|---|---|---|
| 显式 device buffer + copy | 固定输入和受控生命周期 | tensor 大小、传输方向、stream 依赖 | Async 名称不保证与 compute 重叠 |
| pinned / registered host buffer | 设备可见的 host 数据 | allocator、驱动、设备访问能力 | 无显式 memcpy 不代表无总线流量 |
| managed memory | 简化迁移与大数据访问 | HMM/XNACK/设备属性及虚拟化模式 | 更大的可寻址空间不等于本地显存带宽 |
| 多 stream / event | 多路感知和前后处理流水线 | buffer 不提前复用、资源有余量 | 优先级不等于硬实时抢占或 WCET |

**分析：**机器人摄像头回调应将 GPU 工作放入有界异步流水线；控制线程不应每帧等待全设备 `Synchronize`。结果消费前必须完成依赖，输入帧和 buffer 在 job 完成前保持有效。本文没有验证指定相机 DMA-BUF 到 HIP 的直接互操作，不能据 GPU 的共享地址能力宣称整条相机链零拷贝。

## 5. PyTorch 与 vLLM：学习和模型服务分开部署

PyTorch 安装页按 ROCm release、GPU family、OS、Python 和框架版本给出 Docker/pip 组合。例如 `rocm/pytorch:rocm10.1.0_ubuntu24.04_py3.12_pytorch_release_2.14.0` 是文档提供的镜像 tag；实际部署还需固定 image digest。验证至少检查 `torch.__version__`、`torch.version.hip`、设备名以及 `torch.cuda.is_available()`。后者只证明设备可见，不能证明视觉/VLA 模型所有算子均由优化 GPU kernel 执行。@@AMD_ROCm_PyTorch@@

训练部署涉及模型代码、自定义扩展、精度、checkpoint、优化器与通信库；推理部署涉及算子、KV cache、并发、预处理和输出契约。ROCm release notes 保留 MI350 某些训练配置的回归：一组 BERT/RoBERTa/DistilBERT/GPT2 场景训练时间增加 6–22%，另组恢复/未完全解决的模型配置增加 9–25%。这是相应配置的已知问题，不能当作全平台普遍变慢，也不能写成已全部修复。R9700 的特定 LlamaFactory/Unsloth reset 问题标为 resolved，只支持该问题状态。@@AMD_ROCm_Release@@

vLLM 面向 token 生成服务，适合上层交互/推理服务，不能代替 ROS executor 或关节控制器。10.1 安装页的 Python 路线固定 PyTorch 2.13.0，Flash Attention 2.8.3、AITER 0.1.22.post2.dev0，提供包含 ROCm/commit/build-date 的 vLLM 0.29.1.dev0 wheel，并要求 tensorizer 2.12.1 workaround。矩阵的“vLLM 0.29.0”与该 dev wheel 应分别记账；换成 PyTorch 2.14 并不自动构成经过 AMD 文档验证的新组合。@@AMD_ROCm_vLLM@@

**分析：**多机器人模型服务的设计应分别测 prefill、decode、请求排队、取消/超时和 GPU 显存水位；端侧策略推理则测 frame-age、batch=1 时延与丢帧。token/s 不能换算成策略调用频率。机器人上传观测到远端 GPU 服务还增加网络、序列化和失联处理条件，本文不将它描述成实时本体闭环。

## 6. MIGraphX / ONNX Runtime：GPU 图推理入口

MIGraphX 是 ROCm GPU 的 ONNX 图优化/执行引擎，当前安装页列 2.18.0 与 GPU 架构支持；ORT 1.29.0 通过独立 MIGraphX EP plugin 使用它。它与 Ryzen AI 或 Versal 的 `VitisAIExecutionProvider` 是不同后端。保存 ONNX 有助于框架交换，编译图、选定 kernel 和缓存仍与后端/硬件/版本相关。@@AMD_MIGraphX@@ @@AMD_ROCm_ORT@@

一个容易失误的依赖是：当前 ORT 插件 wheel 依赖 `migraphx-libs`，因此需要先从 MIGraphX pip repository 安装；仅装系统包或 tarball 不能满足 pip 的这项依赖。插件还需显式注册，其官方检查流程如下（仅核验文档，没有执行）：

```python
import onnxruntime as ort
import onnxruntime_ep_migraphx as m
for name, path in zip(m.get_ep_names(), m.get_library_paths()):
    ort.register_execution_provider_library(name, path)
print(ort.get_available_providers())
# 文档预期包含 MIGraphXExecutionProvider
```

不同 release 的 ORT 安装页并存旧 monolithic wheel 和新 plugin 路线；10.0 的 soname workaround 不能不加版本条件地套到 10.1。EP 可见后，应用仍应验证实际 provider assignment、输入 dtype/shape、预处理一致性和数值误差。本文取得的是安装/支持证据，未取得目标 VLA 的完整 MIGraphX 算子覆盖、动态 shape profile、workspace 或端到端 benchmark，不能承诺它对任意 ONNX 模型获得优化收益。@@AMD_ROCm_ORT@@

## 8. AMD Quark：同一量化工具的后端契约

Quark 为 PyTorch 与 ONNX 模型提供量化工具，校准数据、量化配置与后端算子约束共同决定产物。Ryzen AI 的 FP32 CNN/Transformer 可以直接交给 EP，在编译时转 BF16；INT8 CNN 则推荐 Quark，也允许相应第三方 QDQ 格式。XINT8 使用对称 INT8 activation/weight 与 power-of-two scale；A8W8、A16W8 的 float scale 配置另列。量化页中的容器 dtype、对称选项和整数表示需一起看，不凭名称推断全部 signedness。@@AMD_RyzenAI_Quantization@@

Vitis AI Gen2 6.3 的 INT8 指南采用 **VINT8** 配置，并要求 `Int32Bias=False`、`enable_npu_cnn=True`，明确配置 DedicatedQDQPair 与 QuantizeAllOpTypes；不能把 Ryzen 的默认 XINT8 字符串原样当作 Versal 配置。BF16 自动转换不要求预先 Quark 量化；混合精度可将敏感算子留在高精度，但是否编译、是否落 CPU 必须读分区报告。@@AMD_VitisAI_Gen2_Quantization@@

```python
# Vitis AI 6.3 Gen2 文档的配置摘录；不是 Ryzen AI 通用配置
from quark.onnx import ModelQuantizer, QConfig
config = QConfig.get_default_config("VINT8")
config.global_quant_config.extra_options["Int32Bias"] = False
config.global_quant_config.enable_npu_cnn = True
config.global_quant_config.extra_options["DedicatedQDQPair"] = True
config.global_quant_config.extra_options["QuantizeAllOpTypes"] = True
quantizer = ModelQuantizer(config)
# 还需提供代表性 CalibrationDataReader，再调用 quantize_model。
```

官方把随机数据量化列为 testing-only 选项，真实校准样本才是生产推荐路径。**分析：**具身校准样本需覆盖照明、运动模糊、距离、遮挡与目标分布；应固定 preprocessing、校准集 hash 和独立留出集，验证检测/位姿/动作指标，而非只对比 tensor 平均误差。MinMSE 优化量化噪声并不直接证明真实任务成功率保持。Quark 的通用能力也不取消 Ryzen/Vitis 所规定的支持配置。@@AMD_VitisAI_Gen2_Quantization@@ @@AMD_Quark_RyzenAI@@

## 9. Ryzen AI ONNX 编译、回退与缓存

ORT `InferenceSession` 加载模型、Vitis AI EP 划分子图，受支持子图到 NPU、其余到 CPU，`session.run()` 提交 tensor 并取得输出。Ryzen 编译指南建议 ONNX opset 17；与 Versal Gen2 推荐 opset 20 的指南分开使用。输入名、shape、dtype 由 `get_inputs()` 等 metadata 获取，不能假定所有视觉模型都接受同一 RGB/NCHW 形式。@@AMD_RyzenAI_Compile@@

| 模型 / APU | 后端选择 | 关键 provider 配置 | 版本与回退边界 |
|---|---|---|---|
| INT8，STX/KRK 及更新设备 | X2 默认；可按文档试 X1 | target；不得设置 PHX xclbin | 新 compiler 不保证每模型比 X1 快 |
| INT8，PHX/HPT | X1 | 指定 phoenix/4x4.xclbin | 旧 1x4/Nx4 文件不再支持 |

| 发布时 context | ORT EP Context Cache | ep.context_enable/file_path/embed_mode | 推荐冻结预编译 context；仍要验证硬件和 runtime |

EP 透明分区使应用易接入，却可能掩盖 CPU 回退与多次数据交接。应导出 operator assignment report：设置 `XLNX_ONNX_EP_REPORT_FILE` 并让 cache 落盘，记录哪些节点/子图真正执行在 NPU/CPU。当前路径的支持算子页仍明确标 **Ryzen AI 1.8.0**，因此只能作该版本的候选覆盖参考，不能冒充完整的1.9支持表。具体 shape、属性、图划分和 compiler 错误仍影响落点；“支持 Conv/MatMul”不能推导任意 Transformer/VLA 全图落 NPU。@@AMD_RyzenAI_Compile@@ @@AMD_RyzenAI_Ops@@

发布包需包括匹配的 ORT/EP/runtime DLL 或 Linux 库、预编译模型以及所需配置/设备 binary。应用应先检查 NPU 类型与 driver compatibility，再创建 EP。AMD 推荐正式应用用 EP Context Cache，开发缓存不得跨驱动/EP 版本复用。AES256 context 加密选项只解决相应模型文件保护；文档中的 Python `encryptionKey` 与 reference `encryption_key` 写法不同，应以实际包 API 验证，不能把样例 key 复制进产品，也不能将文件加密当作启动链认证或权重许可。@@AMD_RyzenAI_App@@ @@AMD_RyzenAI_Compile@@

## 11. Vivado、Vitis、HLS 与加速库：模型之外的数据通路

Vitis 面向自适应 SoC 的软硬件协同开发。Host C/C++ 程序通过 XRT 与硬件交互；PL 内核可来自 HLS C/C++ 或 RTL，AI Engine 算法由对应 compiler 编译，平台提供连接、时钟、内存与设备描述。模型 compiler 解决神经网络映射，Vitis/HLS 解决图像、DSP、数据搬运或运动计算的定制实现；不能用一个 ONNX 文件代替平台硬件设计。@@AMD_Vitis_Product@@

![AMD 官方 Vitis 设计流程图](@@FIG:02_vitis_design_flow@@)

图中 Host、XRT、driver、AXI 和 PL kernels 显示软件调用与硬件互连分别承担什么工作。这是产品级流程图，不是特定 KR260/VEK385 的已通过时序收敛设计；具体 XCLBIN/PDI、连接配置和时钟约束仍须来自选定平台。@@AMD_Vitis_Product@@

典型开发过程是选定器件/平台→综合 HLS 或 RTL 内核→连接 AXI stream / memory mapped 接口→布局布线并生成硬件产物→配套驱动与 device tree→编译 host 应用→板上验证。**分析：**摄像头缩放、色彩转换与归一化适合连续流的数据通路；收益来自减少 CPU 工作和中间 DDR 往返。收益成立还需要输入输出速率匹配、FIFO/背压设计、像素格式与行对齐正确，单个 HLS 内核的 initiation interval 不等于机器人感知的端到端时延。

Vitis Libraries 仓库可见 vision、dsp、motor_control、blas、solver、data_mover 等算法模块，代码仓库采用 Apache-2.0。它们是可组合的构件；库名含 motor_control 不证明已有适配所有伺服驱动、关节总线和保护逻辑的机器人控制产品。工程仍需核验具体函数模板、位宽、target、clock、资源和数值误差。@@AMD_Vitis_Libraries@@

维护状态不能省略：仓库明确从 **2025.2** 起停止维护 PL 的 codec、data_analytics、data_compression、graph、hpc、quantitative_finance、sparse 库；以前 release 仍可取用，AI Engine Libraries 不受这一变更影响。同一 release 开始引入 Vitis IP Libraries。旧教程中的函数存在不意味着当前受维护，生产工程应把库版本/commit 和停维护风险记录到依赖清单。@@AMD_Vitis_Libraries@@

### 13.2 编译结果是模型、目标和配置的契约

通过 Vitis AI EP 创建 ORT session 驱动主机侧编译；provider options 指向原模型、JSON config、VAIML target 和缓存位置。默认输出是 **`.rai` flat-buffer 文件**，将模型 binaries、metadata 和 execution graph 打包，并支持 memory-mapped loading。开发时设置 `keep_outputs=true` 可保留完整 cache directory 及报告；选择目录模式必须复制整目录，不能挑一个 AIE ELF 当成全部模型。`.rai` 的 mmap 是加载机制，不直接证明整个摄像头→CPU→NPU→后处理链没有拷贝。@@AMD_VitisAI_Gen2_Compile@@ @@AMD_VitisAI_Gen2_Output@@

编译报告 `final-vaiml-pass-summary.txt` 记录 model signature、target device、precision、VAIP/FlexML 版本、overlay、NPU clock、DP/TP、supported/offloaded operators、CPU partitions、编译错误和低于阈值分区。报告里的样例 NPU 频率 1267MHz、TP=6、2% GOPs threshold、最多 7 subgraphs 和编译时间是该示例的记录，不能充作所有部署的默认值或实测基准。需要区分“算子支持”与“实际卸载”：阈值、分区数量、编译失败都可能把支持的算子留给 CPU。@@AMD_VitisAI_Gen2_Output@@

| 模型状态与目的 | 选择 runtime | 上板必备产物 | CPU 行为 / 约束 |
|---|---|---|---|
| 初次导入、需要 ONNX 生态或广泛 fallback | ORT + Vitis AI EP | `.rai`/cache、原 ONNX、原 JSON、应用 | 不支持的 subgraphs 在运行时回退 CPU |
| 全图成功卸载、希望直接使用 HW tensor | VART ML | `.rai`/完整 cache、C++ 应用 | 不依赖原 ONNX；没有任意算子的运行时 fallback |
| 模型已编译 CPU partition | VART ML | 异构 compiled model 与 C++ 应用 | CPU/NPU 分区在编译时确定，CPU operator 范围有限 |
| 编译目标/模型签名/缓存不匹配 | 重新验证并编译 | 匹配的模型、config 和目标 runtime | EP 找不到/不匹配编译模型时不会部署到 NPU |

ORT session 必须加载编译时的原 ONNX 和原 config；缓存可以移目录，但位置参数必须指向正确的产物。VART ML 直接读取产物，不要求原 ONNX。厂商将 VART ML 推荐用于性能部署，但这只说明 runtime 设计，不是本章实测吞吐结论。@@AMD_VitisAI_Gen2_Deploy@@

CPU partition 路线执行 `init`→`vaiml_partition`→`vaiml_cpu_partition`→connectivity→`create_cache`。它把受支持的 CPU operators 也编入模型，使 VART ML 能执行异构图；不能认为它包含 ORT CPU EP 的所有算子。**分析：**有 CPU/NPU 交替时须测每个 partition 的数据转换/同步/等待，NPU offload 百分比高也可能被少量 CPU 算子拖慢。目标 VLA 的动态 shape、attention、workspace 和采样逻辑需要逐图编译及日志，目前没有这类目标模型的完整证据。@@AMD_VitisAI_Gen2_CPU_Partition@@ @@AMD_VitisAI_Gen2_Architecture@@

## 14. VART ML 与 VART-X：张量、内存所有权、并发和视觉几何

### 14.1 API 架构和 tensor view

![AMD 官方 VART ML 层次架构](@@FIG:02_vart_ml_architecture@@)

Application 管理流水线，API 层提供 `RunnerFactory`、`Runner`、`NpuTensor`，下方 runtime/platform 管理模型调度、设备与硬件 buffer。图支持这种职责划分；不能由图推导所有对象都跨平台 ABI 通用。以下 API 和线程安全说明采用 **Gen2 6.3** 文档。@@AMD_VitisAI_Gen2_Architecture@@

`RunnerFactory::create_runner(RunnerType::VAIML, model_path, options)` 创建 runner；`get_tensors_info(direction, type)` 查询 name、dtype、shape、strides、layout、size；`get_quant_parameters(name)` 提供量化信息。应用应先读取实际 metadata 再配置前处理，不凭“ResNet50 输入”写死 buffer 大小。输入、输出 tensor view 可独立选择，也可以按名字覆盖，边界是否暴露 CPU/HW view 受编译图拓扑约束。@@AMD_VitisAI_VART_App@@ @@AMD_VitisAI_Gen2_Architecture@@

CPU view 对应 ONNX 标准格式，例如 NCHW、FP32、`[1,3,224,224]`；HW view 可能为 HCWNC4、BF16、`[224,1,224,1,4]`。这是文档示例，不是每个模型固定格式。选 CPU view 时 runner 转换到内部格式并产生拷贝；选 HW view 时应用必须准备正确的布局、padding 和数据类型。不能把原始 RGB/NV12 帧直接解释成已经满足 NPU tensor 契约。@@AMD_VitisAI_Gen2_Architecture@@

| TensorType / memory | runtime 行为 | buffer 生命周期 | 优化成立条件 |
|---|---|---|---|
| HW + XRT_BO | 支持零拷贝输入/输出路线 | runner allocation 为 RAII；用户 BO 由 caller 保持 | bank、size、layout、同步正确 |
| HW + DMA_FD | 接 V4L2、dma_heap、ISP 等可见 buffer | caller 保持 fd/底层 buffer | CMA/硬件可见且格式一致 |
| HW + USER_POINTER_CMA | 使用硬件可见连续内存 | caller 持有 | allocator、物理连续和 cache coherency 满足 |
| HW + USER_POINTER_NON_CMA | 构造 `NpuTensor` 抛 runtime_error | 不应作为可用 HW route | `malloc/new` 指针不能冒充 NPU 可见内存 |
| CPU + 任意 memory type | runner 格式转换，发生 copy | 依分配方式管理 | 简化 bring-up；不能宣称 tensor 零拷贝 |

`NpuTensor` 包装用户内存时不接管所有权；caller 必须在 tensor 和未完成 job 使用期间保持有效。`allocate_npu_tensor` 分配的内存由 tensor RAII 释放；`allocate_sub_tensor` 通过引用计数共享 parent buffer，仅支持一层嵌套。`sync_buffer` 控制显式同步，`export_buffer` 导出 DMA-BUF fd；导出句柄只是互操作入口，另一设备仍需支持导入和同一内存格式。@@AMD_VitisAI_Gen2_Architecture@@

### 14.2 Async、DP/TP 与背压

![AMD 官方同步与异步推理时间线](@@FIG:02_vart_async@@)

同步 `execute` 阻塞调用线程；`execute_async` 返回 JobHandle，可通过 `wait` 或 callback 完成。图显示 host 工作和 NPU 计算可重叠，不提供数值加速比。Gen2 单 runner 的 execute、execute_async、wait 有线程安全说明，callback 在内部 worker thread 执行；共享结果队列仍需应用同步。执行 API 用 `StatusCode`，构造/查询可能抛异常，不能只处理一个错误渠道。@@AMD_VitisAI_Gen2_Async@@ @@AMD_VitisAI_Gen2_Architecture@@

每个 in-flight job 需独立 input/output buffers；`RESOURCE_UNAVAILABLE` 表示内部 slots 已满，应等 job 完成后重试。官方 `vart_infer_async` 样例默认两个并发 job，读取一个 IFM batch，重复提交同一内存数据，只支持一个输入 tensor。样例的 FPS/平均推理时间因此不是多相机真实帧采集结果，也没有证明观测年龄、P99 或电机反馈闭环。**分析：**感知服务应限定队列深度，控制侧按 timestamp 拒绝过时结果；无限排队即使提高平均吞吐也可能使机器人使用旧观测。@@AMD_VitisAI_Gen2_Async@@

Gen2 一个 compute block 为 4×4 的 16 AIE tiles。`dp_size` 复制整个模型处理不同请求，`tp_size` 把一个请求分配到多个 blocks；默认 DP=1、TP=0 由 compiler 自动选择。文档举例 ve2-xc2ve3558 六 blocks（96 tiles）、ve2-xc2ve3858 九 blocks（144 tiles），另有 3858 的推荐 6×4 columns 配置；最终应看 compiler 实际 resolved 值及可用 overlay，不按最大 tiles 强配。DP 提高并发容量不自动降低单帧时延，TP 降时延的效果还受模型、通信和 DDR 限制。@@AMD_VitisAI_Gen2_Tenancy@@

### 14.3 VART-X 的视频对象和前后处理契约

VART-X 的 `Device::get_device_hdl(dev_idx, xclbin_loc)` 为模块提供设备；使用硬件 accelerator 时需匹配 XCLBIN，无需 bitstream 的模块可不设该路径。`VideoFrame` 支持自分配 XRT/NON_CMA、包装 DMA-BUF fd、XRT BO 或 caller pointers，伴随 `VideoInfo` 的尺寸、padding、alignment。`PreProcess` 可选择 `IMAGE_PROCESSING_HLS` 或软件实现，执行 resize、color conversion、normalization、quantization；这些选项必须与模型 mean/scale 和 quant parameters 一致。@@AMD_VitisAI_VART_App@@

DEFAULT 拉伸、LETTERBOX 保比例加 padding、PANSCAN 中心裁剪再缩放的几何不同。PostProcess 解释模型输出，MetaConvert/InferResScaleInfo 将结果映射回原图，overlay 绘制可视化；如果忽略 crop offset 或 letterbox padding，框在模型图里正确也可能在相机坐标里偏移。**分析：**机器人感知桥还需把该原图结果与相机标定、深度、frame_id、采集 timestamp 绑定，得到有单位和坐标系的世界观测；本章不把 2D overlay 当成已经完成 3D 抓取接口。@@AMD_VitisAI_VART_App@@

## 15. XRT：BO 同步、kernel 调用与新 NPU 路线

![AMD 官方 XRT 层次图](@@FIG:02_xrt_layers@@)

XRT 文档 Master 图把应用/API、用户态 runtime、内核驱动和硬件分层。原页 footer 有旧 Last updated 日期，但内容已有 NPU 术语；本章将它标为 **Master 文档快照**，不据此声称是特定 release 的完整支持图。Ryzen AI Linux 所带 XRT DEB、Vitis AI board runtime 与 Master 文档不能互相替换版本。@@AMD_XRT_Docs@@ @@AMD_RyzenAI_Linux@@

经典 FPGA native route 是 `xrt::device`→`load_xclbin` 得 UUID→`xrt::kernel(device, uuid, name)`→按 `kernel.group_id(arg)` 分配 `xrt::bo`→map/write→向设备 `sync`→提交 `run`→`wait`→回读同步。BO 的 bank/group 必须对应 kernel 连接；host pointer 已写不等于设备已看见，job 完成不等于 host cache 已更新。复用 BO 可减少频繁分配，但等待和回收顺序必须正确。@@AMD_XRT_Native@@

Master native API 同时增加 NPU ELF 与 `hw_context` 路线，并在若干模块使用 experimental headers；文档提醒 API 可能 breaking change。ELF/hw_context 是特定执行路径，不能把旧 `load_xclbin` 示例直接当成当前 x86 NPU 的加载器。部分 BO flags 在所有 driver 上并不一定被实现；“都叫 XRT”不证明驱动、buffer sharing、scheduler 或 ABI 完全相同。@@AMD_XRT_Native@@

**分析：**工程应把平台 runtime/driver、硬件 UUID/产物 hash 和应用 ABI 一起固定。相机 DMA-BUF、VART tensor 与 PL BO 互联时，逐边核验 exporter/importer、memory bank、layout、cache 同步和未完成 job。零拷贝是特定边上的有条件结果，不是 XRT 的全平台属性。

## 17. OpenAMP、domain YAML 与 Zephyr：推理和实时控制的分工

EDF domain 配置通过 YAML 指定 CPU、memory、device access 等，再生成各 domain 的设备描述。reserved memory、CMA、remoteproc/rpmsg、vring、mailbox 是跨 Linux 与其他核通信的重要接口；合并多个 YAML 时 domain name 需匹配。它解决资源描述和软件构建，不能凭 YAML 文件存在证明访问隔离、缓存干扰上界、故障隔离或安全认证。@@AMD_EDF_Domains@@

|---|---|---|---|
| Linux APU / x86 CPU | 模型、感知、ROS、规划、运维 | 带 timestamp/frame_id 的观测和轨迹 | 调度/内存/驱动抖动，结果新鲜度 |

## 21. Profiling、运维与许可：原型到生产还缺什么

### 21.1 指标工具不是任务性能证明

Ryzen AI NPU Analyzer 当前仅支持 BF16，明确不支持 INT8；ORT profiling 还能显示 CPU 层。工具把 cycles 换算为时间的 NPU clock 可编辑，应核对实际设备频率，不用默认频率推导所有功率模式的时延。`xrt-smi` 提供 examine/validate/configure；Linux estimated power 不可用，PHX/HPT 又不支持 GEMM 与功率项。例子的 latency 来自 noop，throughput 来自 shim DMA loopback，GEMM 是 full array 测试，51.3TOPS、84.2µs 等样例不是目标神经网络或机器人实测。@@AMD_RyzenAI_Analyzer@@ @@AMD_RyzenAI_SMI@@

ROCm 的 SMI、Systems/Compute profiler 和 SDK 覆盖设备状态、系统 timeline、kernel counters 等不同维度；Vitis AI 的 compilation summary、runner sample 与应用 pipeline logs 也有不同范围。**分析：**核验时先定位 CPU fallback/shape 转换、copy、等待与并发，再优化 kernel。记录 batch、分辨率、精度、warmup、采样数、功率/clock、是否含预处理/RPC；仅看到设备 utilization 高不能判断机器人响应更快。@@AMD_ROCm_Compatibility@@ @@AMD_VitisAI_Gen2_Output@@ @@AMD_VitisAI_Gen2_Async@@

### 21.2 EDF 明确没有承担生产 OSV 的长期维护责任

EDF Production Deployment 指南明确：AMD 不是 OS vendor，不为 Versal/Zynq families 提供 production-grade software、长期软件更新/compliance attestation/SLA。EDF 没有 maintained production update feed、快速 CVE scanning、现成 production boot validation/key revocation 流程，超出 upstream support 后也不继续提供 kernel LTS。指南的 2026.1 base kernel 为 6.18，`linux-xlnx` source fork 是源码路径，不是有生产支持承诺的 OS。硬件长期供货不能填补这一责任。@@AMD_EDF_Production@@

**分析：**量产可选择自行维护 Yocto 或与 OSV 合作，建立 kernel/driver/BSP backport、CVE triage、SBOM、签名 boot/rootfs/model、恢复测试与持续更新责任。RAUC、Mender、OSTree、swupdate 等是可考虑的外部路线，本文没有核验它们在目标 AMD board 上的完整集成，不能把这些名字列为 EDF 已交付的 OTA 服务。Linux 镜像、boot firmware、PL 硬件和模型需作为兼容组合滚动更新；发布/回退前要确认未完成 job、buffer、配置与设备状态的一致性。@@AMD_EDF_Production@@ @@AMD_EDF_Release@@
