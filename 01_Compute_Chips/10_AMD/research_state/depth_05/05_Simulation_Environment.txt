## 2. Genesis：从场景对象追到状态和控制

### 2.1 资产、构建阶段与两条计算链

`Scene` 同时包含 simulator 与 visualizer：前者承担 physics solvers，后者承担分辨率、刷新与视角。`add_entity` 的 morph 描述几何/文件输入，material 描述物理类型，surface 描述可见表面。教程的地面为 Plane，机器人来自 `xml/franka_emika_panda/panda.xml`。这条路径明确了“机器人结构进入仿真”的入口，未完成材料标定或实物关节辨识。@@AMD05_Genesis_Blog@@

![AMD教程：Scene物理与可视化划分](@@FIG:scene@@)

图把 time/gravity 和 resolution/refresh 分属两侧。读图应关注两种频率和开销来源；它不证明关闭 viewer 后相机生成免费，也不证明显示 FPS 等于接触求解速率。

![AMD教程：Entity与资产对象](@@FIG:entity@@)

图列出 URDF、MJCF、mesh 与 primitive。文件格式可解析不代表不同引擎拥有同样惯量、接触参数或执行器动态。跨引擎转换需保留质量、惯量坐标、碰撞 mesh、摩擦、关节上下限与执行器定义，并用同一小任务对照。

`scene.build()` 不是无意义的初始化：教程说明此时检查实体、生成 kernel，分配状态、接触与控制器 buffer。研究性分析：首次构建/编译必须与稳态 step 分开计时；改变 batch 或场景结构可能改变生成代码与内存需求。多环境可以摊薄构建成本，却可能增加接触和状态容量，不能只按机械臂数量线性外推。@@AMD05_Genesis_Blog@@

### 2.2 重置不等于运动，IK不等于安全规划

教程 Panda 有七个臂关节与两个夹爪 DOF，示例设置 `set_dofs_kp/kv/force_range`。`set_dofs_position` 直接覆盖内部状态并绕过物理求解，适合 reset；`control_dofs_position/velocity` 才通过 PD 生成实际运动。若用直接写状态的方法评估跟踪误差，控制动力学会被人为消除。示例增益和力矩范围只支持该教学场景，不能当真实 Franka 或任意本体的合规控制配置。@@AMD05_Genesis_Blog@@

控制链为目标末端位姿→IK关节配置→起终点插值→逐步PD跟踪→constraint/contact求解→积分→状态更新。IK只回答几何可达性；整段轨迹还需验证自碰撞、障碍碰撞、速度/加速度、夹爪状态与奇异附近的跳变。初始化赋值“到位”与真实执行“到位”分母不同，报告应分别统计。教程未给完整避障规划与失败处理实验。@@AMD05_Genesis_Blog@@

### 2.3 时间与批量并行的测量边界

教程设置 `dt=0.01`、重力 `(0,0,-10.0)`、`show_viewer=False`，循环120次；分析计算对应1.2秒模拟时间。墙钟耗时未知，因此不能称实时、快于实时或100Hz实机控制。九环境例子 `scene.build(n_envs=9, env_spacing=(1.0,1.0))` 共享场景结构和GPU kernel，各状态多一个 environment 维度。有效批量应确保 reset、目标、done、奖励和seed均按环境独立处理，防止一份动作广播到所有环境却被当成九份策略经验。@@AMD05_Genesis_Blog@@

![AMD教程：九Panda环境](@@FIG:parallel@@)

图确认九环境场景存在；它没有 wall-clock、求解步数、contact数量、相机配置、batch吞吐或 RL 成功分母。AMD 教程所称适用于 RL/large-scale evaluation 是用途说明，本章不补造学习曲线。

当前上游 README 将 physics、rendering 和 compiler 分层：Quadrants 将 Python kernel 降到 CUDA、AMD ROCm、Metal、Vulkan、x86和ARM64，携带 autodiff、GPU graphs 与cache；当前文档安装包为 `genesis-world`。这些是上游公开能力，仍需核每个 solver/coupler/renderer 的实际依赖和目标后端。尤其不能仅凭统一 Python API 推导 Nyx 与全部相机/粒子/软体组件在所有后端行为一致。复建应冻结 commit、安装 extra、驱动、Torch和运行日志；旧 Genesis 教程与新 World 主分支分别建环境。@@AMD05_Genesis_Repo@@ @@AMD05_Genesis_Docs@@

## 3. MuJoCo与MJX：接触近似、设备状态和批量基准

MuJoCo 是以机器人动力学为核心的第三方引擎，CPU路径与GPU学习路径须分开。上游 MJX 文档明确 MJX-JAX 支持 NVIDIA/AMD GPU、Apple Silicon、TPU；该上游快照将 MJX-Warp 描述为专门优化 NVIDIA GPU。另有2026-09-29 AMD XArm-6案例，使用随案例补丁提供的ROCm MuJoCo Warp实现在MI300X/MI355X单卡训练。故不能据上游文字断言Warp在AMD上绝对不可用，也不能把该案例推广为上游包全部功能/SKU的无修改支持。@@AMD05_Mujoco_Overview@@ @@Model05_NVIDIA_08_DEEP_MUJOCO_MJX@@ @@AMD06_XArm_Sim2Real@@

设备链从 `mujoco.MjModel.from_xml_string/path` 编译模型开始，通过 `mjx.put_model` 和 `mjx.make_data` 建立设备结构，随后 `mjx.step`；示例用 `jax.vmap` 批量化、`jax.jit` 编译。模型结构、设备动态数组和 host 数据不是同一个对象。研究性建议：计时前等待设备完成，区分 JIT、host/device搬运、逐step观测读回和渲染；每步把大型数据读到CPU可能抵消批量收益。JAX API相近也不是完整功能等价，上游文档明确存在不支持的功能。@@Model05_NVIDIA_08_DEEP_MUJOCO_MJX@@

接触模型是物理近似而非真值。计算文档解释，convex formulation 放松严格互补性，使接触法向力与速度可能同时为正；摩擦不必最大耗散。优势是更适合数值求解，但插接、滚动、轻物体抓取等任务应对接触/摩擦参数敏感性做留出试验，不能用“没有穿透画面”判断力学正确。模型中的 actuator activation 同样影响控制时延：`filter` 的Euler积分在时间常数t<h时可发散；`filterexact`采用解析积分，对正时间常数稳定。这并不让整个系统的接触求解、碰撞或策略天然稳定。@@Model05_NVIDIA_08_DEEP_MUJOCO_COMPUTATION@@

### 3.1 AMD两次训练教程与真实迁移的增量证据

2026-03-31教程在RX7900XTX、Ubuntu24.04、ROCm7.2上用MJX-JAX训练XArm7；环境设置osmesa软件渲染并关闭XLA command buffer，因此不能以该教程推导GPU相机渲染吞吐。模型mesh需降面并限maxhullvert20；初始化IK和缓存Jacobian用来对小物体位置扰动做线性修正，避免训练期反复求IK，不能外推大范围运动精度。八维动作对应七关节及夹爪；phase-gated奖励和latched grasp/lift标志稳定训练信号，但接触随后丢失仍需单独判定任务结果。50M timesteps、10eval是命令配置，未给目标GPU同条件训练秒数或实物成功分母。@@AMD06_XArm_JAX@@

2026-09 XArm6案例从真实单关节响应拟合arm/gripper模型，模拟固件重力补偿和API延迟，用实测范围随机化块质量、初始状态与延迟；奖励改为orientation-aware caging，再加入历史状态和平滑奖励适配servo_streaming。真实部署用传统双D435i感知替代仿真特权块位姿，固定upright方向，MLP导ONNX后40Hz调用；并非图像直接进入视觉策略。官方称zero-shot sim-to-real，其含义是该训练策略转到该标定场景，并非无需真机测量、无需感知标定或对任意物体泛化。全文未披露试验次数、任务成功率分母或P99/WCET。@@AMD06_XArm_Sim2Real@@

![AMD官方：训练策略进入真实控制链](@@FIG:xarm_controller@@)

图中Vision estimates与机器人状态进入观测，策略生成目标再经command/robot API执行。图写“7 joint + 1 gripper”，正文Environment Details写六个关节delta加一个gripper delta，存在动作维数冲突；本章保留原图，按正文描述XArm6，部署前必须核模型输出shape和SDK映射。它支持同一策略槽位被真实感知替代的机制，不能证明40Hz是电机servo频率。下载入口robotics.zip实际href为页内片段，当前归档未取得独立ZIP原件，不能称补丁已复建；正文已核官方声明与完整控制图，补丁/参数范围仍需可下载附件核验。

## 4. Gazebo：传感器并不是加一个标签就完成系统仿真

Harmonic文档标识支持周期2023-09至2029-05；这是 Gazebo 项目版本生命周期，不能当AMD BSP支持期。SDF world中需显式加载physics/scene broadcaster，IMU等传感器还要加载对应system plugin；sensor标签定义link、always_on、update_rate、topic。IMU示例的update_rate为1，是教程设置而非机器人目标IMU频率，且文档提示并非所有sensor支持所有标签。@@AMD05_Gazebo_Docs@@ @@AMD05_Gazebo_Sensors@@

Gazebo transport到ROS不是自动同义转换。`ros_gz`桥需要消息类型和方向，参数/YAML/launch composition与QoS是接口契约的一部分。相机大消息可能受到队列、可靠重传或桥接复制影响；分析建议按消息时间戳、实际到达和消费时间分别统计观测年龄。接口允许spawn/delete、state与时间step，不说明一个键盘cmd_vel演示完成了导航、定位、恢复与多机运营。教程内仍存在旧Foxy视频，复建应以当前目标发行版的组合为准。@@AMD05_Gazebo_ROS@@

Classic迁移需要改依赖包、启动接口、插件与消息/桥，不能仅替换命令名。既有KRS安装说明绑定Classic11，硬件加速节点可复用的范围应逐个验证；从旧gazebo_ros插件转到ros_gz还需检验坐标树、时间源、topic命名与控制器驱动。冻结老栈可以复现历史示例，但新项目必须同时评估版本支持和维护成本。@@AMD05_Gazebo_Migration@@ @@KRS_Install@@

## 5. O3DE：资产导入、物理材料和传感器时序的三个边界

### 5.1 ROS组件与导入纠错

O3DE将ROS2 core、Sensors、Controllers、RobotImporter等功能分组；FrameComponent处理TF2的时空关系和namespace，sensor可从frame update或physics event触发。当前文档显示26.05，并专门说明25.05起部分ContactSensor/Spawner/Spawn组件依赖gazebo_msgs；在Jazzy弃用、Kilted缺包等环境下会自动禁用相关组件。因此宣传传感器总表不能直接当所有ROS发行版的可用列表。@@AMD05_O3DE_Concepts@@

RobotImporter解析SDF/URDF/XACRO、解析mesh路径、复制源资产、生成product资产与prefab；关节可以导为articulation或classic joint，fixed joint处理需审核。`Fix URDF` 可补默认mass/inertia或修改名称，解决的是解析/兼容问题。该操作会改变物理模型，应保存修正差异、重新核坐标和惯量，而不是把“导入成功”作为本体标定完成。@@AMD05_O3DE_Import@@

![O3DE官方：URDF修正提示](@@FIG:urdf_fix@@)

截图明确写出惯量缺失、reset to default，并列出links；这正是需要审核修复后的物理参数的证据，不能只截取“execution succeeded”。

### 5.2 材料、接触和时钟

PhysX material规定static/dynamic friction、restitution及combine规则：average/minimum/maximum/multiply；这些值与可见PBR材质分开。Compliant Contact只在PhysX5.1 enabled条件下可用，以隐式弹簧生成法向力，restitution不再按普通反弹参数使用。选择接触机制后需与真实材料摩擦、软夹爪或缓冲结构匹配；拍摄照片、纹理和几何资产不能推出雷达/深度/激光传感器误差正确。@@AMD05_O3DE_Physics@@ @@AMD05_O3DE_Materials@@

ROS2时钟注册项 `/O3DE/ROS2/ClockType` 有realtime、simulation、ros2。realtime从仿真开始的0起计，受墙钟jitter影响且不能运行时调整；默认simulation按physics delta递增，可快慢于真实时间，适合IMU/odometry同步；ros2跟随外部ROS时间。分析建议：统一 `/clock` 和 `use_sim_time`，明确pause、step、reset时间回退与缓存失效；混用墙钟和模拟时钟会造成TF extrapolation、控制超时或观测排序错误。固定模拟时间步消除的是相应时间源抖动，并非CPU调度或消息网络抖动。@@AMD05_O3DE_Time@@

### 5.3 RGL是明确的GPU依赖反例

Robotec O3DE RGL Gem底层raycasting库使用CUDA/OptiX，提供噪声、点云intensity与ray pattern设置。Apache2.0标记描述Gem源码，不能取消CUDA/OptiX及下层库二进制条件。其build表列2505、2409、2310组合，development对2510及更新仅称预期工作且未充分测试。故本章不把RGL或网站性能宣称推广为AMD上已经可用的激光雷达实现；AMD方案须选确证的替代实现或逐项移植。@@AMD05_RGL_Repo@@ @@AMD05_O3DE_Robotics@@

## 6. 合成数据和sim-to-real：建立可验证的误差预算

以下为分析性实验设计，而非AMD公布的完整产品能力。视觉域随机化需覆盖灯光、背景、曝光、镜头畸变、运动模糊和遮挡；动力学需覆盖质量/惯量、静动摩擦、接触柔顺、负载、关节死区、执行延迟与限幅。参数分布应来自系统辨识或真实日志，不能用宽到不现实的随机范围掩盖模型错误。共享结构的batch环境适合改变状态和部分参数，但改变拓扑、资产或shader是否重编译应按具体引擎测量。依据上述模型/材料与build机制提出验证条件。@@AMD05_Genesis_Blog@@ @@Model05_NVIDIA_08_DEEP_MUJOCO_COMPUTATION@@ @@AMD05_O3DE_Materials@@

时间域至少记录physics timestep/substep、camera cadence、IMU cadence、policy调用、动作chunk以及控制器tick。分析例：physics100Hz、camera30Hz时不可能每次physics step都有新图；若未标注图像复用/年龄，训练策略可能偷用了真机不存在的同步观测。动作repeat和horizon改变控制带宽；接触求解在延迟变化时需要重新验证。Gazebo update_rate与O3DE clock机制提供设置入口，不能证明真实传感器噪声、同步和丢帧已被复刻。@@AMD05_Gazebo_Sensors@@ @@AMD05_O3DE_Time@@

## 7. 按任务复建：三个不能互换的实验协议

### 7.1 操作策略：从理想状态转成可部署观测

### 7.2 AMR：桥、地图和失效注入组成系统
