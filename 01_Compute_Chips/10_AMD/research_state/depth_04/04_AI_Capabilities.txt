## 2. 任务地图：语言、感知、操作与控制不是同一个问题

| 任务层 | 输入→输出 | 代表模型/方法 | AMD 证据与适用边界 |
|---|---|---|---|
| 语言理解与任务拆解 | 指令/地图摘要→子任务或工具调用 | Qwen3、Llama、GPT-OSS | Ryzen AI 1.9 制品及 OGA 路线；文本正确率不是任务完成率 |
| 多模态理解 | 图像/视频/语言→描述、定位语义 | Qwen3-VL-4B、VideoChat-Flash | AMD NPU 优化模型卡/官方 VLM 示例；还需外部几何和执行器 |
| 2D 感知 | RGB→分类/框/分割 | 检测、分割、姿态模型 | Vitis AI/ONNX 编译路径，具体型号须目标支持表与算子验证 |
| 3D/深度/定位 | 双目/点云/IMU→深度、位姿、地图 | Stereo、重建、SLAM；DINOv2 等可作视觉特征 | KRS 感知前处理有证据；通用 3D 模型全网络部署未核 |
| 操作 VLA | 相机/语言/本体状态→动作 | π0、π0.5、OpenVLA、MolmoAct2 | π0、MolmoAct2 有 AMD 示例；其余为作者实现/待移植 |
| 模仿策略 | 观测历史→动作序列 | ACT、Diffusion Policy、SmolVLA | 作者实现与 LeRobot 生态；逐模型 AMD 实测尚不完整 |
| 世界模型 | 首帧/动作/上下文→未来视频 | Micro-World 2、上游 Wan2.2 | MI350X 官方训练/推理；不能替代接触动力学 |
| 强化学习/运动/导航 | 状态、目标→速度/关节策略 | MuJoCo 环境中的策略、传统导航栈 | CPU 仿真及 PyTorch 路径可评估；目标全身闭环证据未取得 |
| 编排与几何控制 | 子任务/目标位姿→轨迹/电机命令 | Agent、状态机、MPC、IK、轨迹优化 | CPU/ROS/本体控制器整合；MPC、IK不是基础模型 |

语言层适合处理低频任务选择与异常解释，感知层需要经过标定的几何与时间戳，操作层需要有明确单位的动作表示，下层控制器需要连续可执行命令和失效处理。这一拆分决定模型如何部署：可把 VLM 放 NPU、策略放 GPU、控制放独立 CPU/RPU，但这是建议的系统分工，不是现成 AMD 机器人产品契约。需要验证共享内存、功率、线程与驱动争用是否改变观测年龄和尾延迟。03 的多相机链不能仅因 04 某模型“能推理”就被视为联合验收通过。

## 4. π0 专题：从示范到真实 Koch 执行

### 4.1 模型机制与三个版本的边界

AMD 2025-07-14 教程使用约 3B 的 π0，说明其基于 PaliGemma 视觉语言骨干并结合机器人动作生成。模型作者 openpi 当前 README 则区分 π0 的 flow-based VLA、π0-FAST 的离散自回归动作及 π0.5 的改进版本，并提供 PyTorch 与原 JAX 实现。作者后续版本和 README 主分支不能作为 AMD 2025 教程当时已运行 π0.5 的证据。作者的“10k+ 小时预训练”描述也不等于 AMD 本次微调采集量。@@AMD04_LeRobot_Blog@@ @@Model04_NVIDIA_04_EXP_OPENPI_README@@

流匹配动作专家的计算方式与语言逐 token 解码不同：它在观测和指令条件下迭代更新连续动作序列，再把序列交给机器人执行层。动作 chunk 的好处是减少每个动作都重新请求完整策略的开销，代价是执行到后部时观测已经变旧。遇到物体移动、抓取失败或接触变化，执行层必须决定提前终止、重新观察或重规划，不能只循环消费缓存动作。π0-FAST 以离散 token 压缩动作序列，其吞吐特性也不能直接套给 flow head。AMD 教程没有披露本次 chunk 长度、动作下采样、执行策略及完整 denoising 时延，本文不补数字。

## 5. MolmoAct2 专题：端侧 VLA、动作空间与异步执行

### 5.1 模型身份与依赖

AMD 2026-09-30 博文以 SigLip2 视觉编码器、Qwen3-4B 语言骨干和 flow-matching 动作专家解释 MolmoAct2。官方作者集合列出 MolmoAct2、MolmoAct2-Think、MolmoAct2-Pretrain 和 Molmo2-ER；AMD 博文的“MolmoAct2-ER”用词与作者独立的 Molmo2-ER 名称应分别记录，不能自行认定两个 checkpoint 相同。作者卡实际标称约 5B 的整模型，与 4B 语言骨干参数不是矛盾。部署 revision 应按容器实际下载的权重和配置锁定。@@AMD04_MolmoAct_Blog@@ @@AMD04_Molmo2_Collection@@ @@AMD04_Molmo2_Card@@

作者卡进一步说明，VLM与连续动作专家通过每层KV conditioning连接；基础MolmoAct2是post-trained多本体checkpoint，含norm_stats.json，面向目标本体继续微调，并非某一个部署场景可直接运行的策略。卡指向LIBERO、DROID、BimanualYAM、SO100_101微调版本，部署时须确认Ryzers真正选择了哪一个。视觉语义token的KV被动作专家使用，这也解释为什么可先缓存视觉/语言上下文，但新的相机观测或指令变化时必须更新上下文，不能为省计算重复使用失效cache。@@AMD04_Molmo2_Card@@

### 5.2 末端动作为何能跨本体，也为何仍需适配

末端坐标加夹爪状态将“手应该去哪”与“哪个关节怎样运动”拆开。策略输出的手部位姿/增量进入 IK 或本体 controller，由后者计算关节动作，这能减少策略对具体关节数和关节编号的依赖。AMD 展示 Panda→UR5e/Robotiq85→xArm6 的零微调跨本体仿真。该结果成立于对应仿真模型、末端坐标定义与可达性范围；换成真实本体，仍要对齐基座/工具 frame、旋转表示、长度单位、夹爪幅值及速度/加速度约束。训练中的 Panda、YAM、SO101 名称不等于 AMD 对这些实体所有 SDK 都做过产品适配。@@AMD04_MolmoAct_Blog@@

关节模式则依赖关节顺序、limit、连续旋转定义、encoder offset 与动作单位；不能把末端模式展示的迁移性质套给 joint 输出。IK 得到一个数学解也未必存在无碰撞轨迹，真实执行前还要检验关节速度、奇异点、工具/环境碰撞和轨迹连续性。策略语言输出、几何可达、控制可执行与真实抓取成功应分别统计。

### 5.3 异步 chunk、暂停语义与评估分母

Ryzers 示例给 `THINK=0 NUM_STEPS=4` 的快速交互默认值，`THINK=1` 启用深度推理；`EMBODIMENT` 选择 Panda/UR5e/xArm6，`SUITE`、`TASK_ID`、`SEED` 支持重现。四个动作去噪步骤是模型采样条件，不能解释为每个动作都四个物理 tick。实时 server 让 MuJoCo 按墙钟运行，后台计算下一 chunk；等待时机器人保持当前姿态。实际README确认download脚本预加载MolmoAct2-DROID、DROID-Dataset与MolmoAct2-Think-LIBERO，修正仅由基础集合推断执行checkpoint的风险。这个实现说明模型计算可能形成等待段，并未证明始终无停顿运动。文中 RT_MAX_STEPS 默认 1200 是 episode 步数限制，不是 1200 Hz。@@AMD04_MolmoAct_Blog@@ @@AMD04_Ryzers_Molmo_Readme@@

| 评估路径 | 系统真实做什么 | 适合验证 | 无法证明 |
|---|---|---|---|
| 交互仿真 | 浏览器输入指令、MuJoCo 执行 | 指令/图像/动作链联通 | 实物传感器与电机响应 |
| 跨本体仿真 | 同策略换机器人动力学/控制映射 | 指定末端动作映射 | 任意机械臂零适配 |
| 实时仿真 | 墙钟运行、后台策略、hold pose | 推理与执行调度行为 | 硬实时、安全停止 |
| LIBERO闭环 | rollout 中新观测影响下一动作 | 指定 suite/task 的仿真任务 | 真实部署成功率 |
| DROID开环 | 记录观测输入、比较预测与人工动作 | 分布差异、动作误差 | 模型实际执行后是否成功 |

DROID 记录来自真实环境，但开环误差没有包含“预测动作改变环境后下一帧”的反馈；模型短时接近人工动作仍可能在接触处累积失败。LIBERO 四 suite 各 task0—9 的脚本覆盖不能替代完整种子、尝试次数和成功率表。本次没有取得该 Max+395 配置的完整端到端延迟、稳态温度、精度/量化、P99 与各任务成功率，均保留为待测。尤其不能由“大统一内存能容纳”推出模型并发后还满足控制 deadline。

## 9. 内存、并发与端到端预算

模型容量可以先用参数载荷做筛选，但必须分配activation、KV cache、图像token、中间workspace、多个session、视频解码与控制线程。统一物理内存减少部分复制和容量割裂，但GPU/NPU/CPU仍有带宽、一致性与驱动同步边界。HIP unified memory的page fault/迁移、pinned memory以及stream ordering分别影响首帧和稳态；不能把“统一地址”解释成任意跨设备访问没有开销。@@AMD_HIP_Memory@@ @@AMD_HIP_Coherence@@ @@AMD_ROCm_Isolation@@

建议测四组：策略单独、感知+策略、加入VLM/语音、加入视频录制与后台运维；每组在相同功率模式和温度稳态下记录obs age、policy latency分布、deadline miss、内存高水位和动作缓存余量。不同模型共享GPU时服务端batch吞吐可能升高，单个机器人等待时间却升高；对控制任务，batch1低延迟和可预测性比最大tokens/s更关键。NPU分担语言可减GPU争用，但仍共享DRAM与功率约束，需要目标系统证据。

分析示例：假设执行器以20Hz消费动作、一次chunk包含10点，名义覆盖0.5s；若采集/预处理0.05s、策略/RPC0.35s，则后部动作的观测年龄可能接近0.9s，尚未计队列与执行误差。这个假设只说明chunk吞吐与反馈时效为何不同，不是任何AMD实测。预算应以“新观测到实际动作”的路径制定，P99不等于最坏执行时间，平均实时也不等于安全截止保证。
